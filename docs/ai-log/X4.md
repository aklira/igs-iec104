# X4 — Usage examples

## Request

The maintainer asked for usage examples of the library, in French: first a list of proposals, then the
first six, placed in `crates/igs-iec104/examples/`, and an entry in `IMPLEMENTATION.md`. The crate already
had four examples (client, server, redundancy, TLS), which X2 covers.

## Done

Six programs were added. Each one states in its module comment how to run it and what to expect.

| Program | Shows |
| --- | --- |
| `client_commands.rs` | Select-before-operate of a single command, execution after the confirmation of the selection, a set point to a point the station lacks (refused). |
| `client_interrogation.rs` | One request of each kind: station and group interrogation, counter interrogation, read, clock synchronization, test command. |
| `client_events.rs` | Every event of the client and of its deliveries, for one minute. |
| `client_recovery.rs` | Reconnection with its policy, and a request made while offline, reported as discarded (`OfflineRequests::Discard`). |
| `server_handler.rs` | A station whose application judges selections and executions (address range, time tags, limits), and a clock synchronization. |
| `server_process_image.rs` | Points of four kinds that change while the station runs, two interrogation groups, the unchanged-value case. |

The plan gained task X4 (`IMPLEMENTATION.md`, Phase 5, after X2). The other examples proposed earlier
(redundancy switch, low-level transport, TLS security events, rustls, offline codec) are not written yet.

## Findings during the runs

- **A clock synchronization and a test command are answered by a positive confirmation without a
  termination.** The station of this library works that way (S2), so `client_interrogation` ends those
  requests on the confirmation. A first version waited for a termination and hung on the clock
  synchronization.
- **A refused connection is not reported at once on every system.** On this machine, a connection to a
  closed port on `127.0.0.1` gets no answer, so the attempt waits for the connection timeout (t0). On
  `[::1]` the refusal is immediate. `client_recovery` documents both cases and suggests `[::1]:2404`.
  This is the environment, not the library: the timeout is the one the session parameters give.
- **`TransferState` has three pending states.** `client_events` prints them in one arm instead of
  leaving the match incomplete.

## Verification

Gate on the workspace: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --all-features
-- -D warnings`, `cargo test --workspace --all-features` and `cargo deny check` all pass. `cargo deny`
reports a warning that was already there before this task: `deny.toml` allows the `NCSA` license, which
no dependency uses.

Runs, each against the `server` example (or the server example named in its row) and the examples
of this crate, on loopback:

- `client_commands` against `server` on `127.0.0.1:2411`: the selection and the execution are confirmed
  (the execution with a termination); the set point to point 2 gets a negative confirmation (cause 7).
  The program ends with its final message, exit 0.
- `client_interrogation` against `server`: the six requests complete in order, exit 0.
- `client_events` against `server`: connected, transfer pending then started, interrogation sent, 24
  events received; stopped by the shell timeout after 12 s. The one-minute limit of the program was not
  reached in this run.
- `client_recovery` against `server` started two seconds late on `[::1]:2416`: `ConnectFailed`, then
  `Discarded` for the interrogation made while offline, then `Connected`, the transfer, the
  interrogation, exit 0.
- `server_handler` with `igs104-client`: a single command to point 11 is refused (cause 47), a set point
  of 1000 to point 2 is refused (negative cause 7), a single command to point 1 is accepted.
- `server_process_image` with `client_interrogation`: the station answers the interrogation with its
  points; the updates report changed or unchanged values as expected.
