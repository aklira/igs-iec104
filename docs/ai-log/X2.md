# X2 — Documentation and examples

## Prompt (summarised)

Task X2 of IMPLEMENTATION.md: rustdoc on every public item (`#![deny(missing_docs)]` in
`igs-iec104`), examples for the client, the server, the redundancy and TLS, a README quick start,
a CHANGELOG and an MSRV policy. Done when `cargo doc --no-deps` has no warnings and the examples
compile in CI. Depends on T2 and S2. The maintainer asked for it with "commence X2"; the work stays
in the working tree until a commit is requested.

## Status

**Done in the working tree.** The TLS example, which was missing, was added with the transport
increment of X1 (`examples/tls.rs`). The examples compile in the gate, and the rustdoc build has no
warnings. The box for X2 in IMPLEMENTATION.md §6 is ticked in the commit that adds the TLS example,
as the plan asks.

## Summary

- **Missing docs.** `#![deny(missing_docs)]` in the three library crates: `igs-iec104` (as the plan
  asks), and also `igs-iec104-codec` and `igs-iec104-link`, since the plan asks for every public
  item. The codec had 15 undocumented getters in `formats/times.rs`; they are now documented. The
  link crate and the `igs-iec104` crate already had every item documented.
- **Broken links.** Five intra-doc links in the codec's module docs (`apci.rs`, `asdu/mod.rs`) did
  not resolve, because the module docs are merged with the outer docs in `lib.rs`. They now name
  their target by path.
- **Examples** in `crates/igs-iec104/examples/`:
  - `client.rs`: connects, starts the data transfer, sends a station interrogation and prints the
    events until the termination.
  - `server.rs`: a controlled station with a single-point status that toggles each second and a
    float measurement; it accepts the commands to the status point and refuses the others.
  - `redundancy.rs`: a controlling station with redundant endpoints, printing every group event.
  - Each example uses `#[tokio::main(flavor = "current_thread")]`, because the crate's tokio
    features do not include `rt-multi-thread`. The examples follow the workspace lints (no
    `unwrap`, `expect`, indexing or unchecked arithmetic).
- **README.** Status, a quick start (tests, the server and client examples, the redundancy example),
  the binaries, the documentation build, the MSRV policy, the licence and the standards note.
- **CHANGELOG.md.** An "Unreleased" entry: the added crates and binaries, the known gaps (TLS,
  points from a TOML file, the interop and load tests of S5), and the MSRV.
- **CI** (`.github/workflows/ci.yml`):
  - a `Documentation` step in the gate: `RUSTDOCFLAGS="-D warnings" cargo doc --workspace
    --no-deps --all-features`;
  - an `msrv` job that runs the tests on Rust 1.85. `rust-toolchain.toml` pins `stable`, so the
    job names the toolchain on the command line (`cargo +1.85 test`); otherwise it would silently
    test stable.
  - The examples compile in the existing gate: `cargo clippy --all-targets` and `cargo test`
    build them.

## Decisions

- **TLS example deferred to X1.** It cannot be written before the TLS backend exists. The plan lists
  it under X2, but X2 depends only on T2 and S2. The maintainer may prefer to accept the gap or to
  move the example into X1.
- **MSRV is 1.85**, the existing `rust-version`. Verified: `cargo +1.85 test --workspace
  --all-features` passes. The `msrv` CI job runs the same command.
- **`#![deny(missing_docs)]` in all library crates**, not only `igs-iec104`: the plan's rule is
  "every public item", and the two other crates are published with the same API surface.
- **Examples use the current-thread runtime**, to avoid enabling `rt-multi-thread` in the library's
  tokio features for the examples' sake.

## Verification

- `cargo fmt --all --check`: clean.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`: clean.
- `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features`: clean.

- `cargo deny check`: passes. It prints a warning that the `NCSA` allowance is unmatched; the

  predates this task.
- The examples run against each other on loopback:
  - the server example listens; the client example connects, starts the transfer, receives the
    end-of-initialisation (cause 4), the activation confirmation (cause 7), the station
    interrogation answers (cause 20) and the termination (cause 10), and exits with 0;
  - the redundancy example, given a first endpoint that never connects and a live second one,
    switches to the second, interrogates it, and keeps running.

## Points for the reviewer

- **Dead endpoints in this sandbox.** A connection to a closed loopback port does not fail at once
  here: it hangs until the connect timeout. So the redundancy example was checked with an endpoint
  that never answers, not with a refused one; the group still switched to the live endpoint.
- **Group start order.** The group starts the first endpoint that connects, not the first one in
  the list; the example's docs say so. Preference by list order applies only to the next start
  after a loss.
