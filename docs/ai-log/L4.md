## Design

- **The probe** is `bench/probe`, a workspace member named `igs-iec104-probe`
  (not published). It uses only the public API of `igs-iec104` (`connect`, `run`,
  `Command`, `Delivery`) and the codec's ASDU types. It is a static musl binary
  (`x86_64-unknown-linux-musl`, a target added to the local toolchain; nothing in
  the repository depends on it), copied to `bench/bin/` by the tests.
- **Why the probe is inside the bench network.** The bench runs rootless Podman
  with pasta networking, so the host cannot reach `172.31.104.0/24`. The probe runs
  in its own container (`probe`, 172.31.104.30) of the same netshoot image that
  provides the capture, pinned by digest and already approved for the bench.
- **Both directions.** Direction 1: the probe is the controlling station and
  connects to the reference server (172.31.104.10, controlled). Direction 2: the
  reference client (172.31.104.21, controlling) connects to the probe, which
  listens on 172.31.104.30. The client's target is set by `BENCH_CLIENT_CONFIG`
  (`peer/client-to-probe.json`, the same configuration with the probe's address).
- **Capture.** The probe's own tcpdump records every frame the probe exchanges,
  in both directions, so the same wire checks apply to both directions.
- **Checks.** The probe reports `PASS` or `FAIL`, and the test checks the frames
  of the capture with tshark: which frame was sent by whom, N(S) and N(R), the
  window, and the timing of the acknowledgements.

## Observations of the reference peers (black box)

- The reference client sends STARTDT act and a general interrogation (C_IC_NA_1)
  as soon as the connection opens. It does not send TESTFR act while the probe
  sends its own test acts (5.2: a station that receives test frames does not
  send them).
- The reference server answers an interrogation with ACTCON, its datapoints
  (M_SP_NA_1 and M_ME_NA_1), then ACTTERM.
- The reference client's acknowledgement of eight frames came 2 ms after the
  eighth; its acknowledgement of three more came 10.05 s after the eleventh frame,
  within t2. This is consistent with Q-010 (t2 starts at the first unacknowledged
  I frame): the first of the three was sent at 3.10 s and the acknowledgement came
  at 13.20 s. This is evidence about the peer, not a decision of this repository.
- In the wrap run, the reference client closed the connection about 60 s after it
  opened (a FIN, then a RST). The probe had sent about 10 800 frames by then. The
  cause is not visible from outside. The client's acknowledgements came in bursts
  about 44 ms apart when the window was full, which limits the rate to about
  250 frames per second, so 32768 frames do not fit in one connection of 60 s.
- In captures, Wireshark writes `<-` or `->` depending on which end is controlled,
  not on the sender. Several APDUs can share one TCP packet: the decoder splits
  them.

## Defects found and fixed during the work

- The probe's tcpdump held packets back, so a scenario that ended at once left an
  empty capture. Fixed with `--immediate-mode` on the probe's tcpdump only; the
  capture of the reference server keeps its settings, since F4 waits for its frames.
- The decoder read only the first APDU of a packet; it now splits the packet.
- The direction arrow regex accepted only `<-`.

## Points for the reviewer

- Accept the list above as the scenario list of L4, or change it. The fault
  injection needs a relay, which is new code of the bench: decide whether it
  belongs to L4 or to a later task.
- `d2-wrap` is an expected failure (strict). The reference client's close after
  about 60 s is the peer's behaviour. Changing the client's configuration to make it
  stay open would change the peer, which needs an approval.
- `d1-wrap` needs a command that the server answers once; the interrogation
  answers four frames each time, which is too heavy for 33 000 frames.
- The probe reports the reason of a close through the driver's error; the
  `xfail` reason names the observed close.
