# T4 — Client interop matrix

## Prompt (summarised)

Task T4 of IMPLEMENTATION.md: bench scenarios with the client against the reference server, for
every procedure of T2. Depends on T2 and F4. Done when 100 % of the client matrix passes. The task
is a human gate: the phase 3 exit criterion is reviewed by a maintainer. The maintainer said "OK
pour T4" to start it. The gate itself is still open (see the last section).

Inputs: the T2 client API (`crates/igs-iec104/src/client.rs`), the T3 command-line client
(`crates/igs-iec104/src/bin/igs104_client.rs`), the F4 and L4 bench helpers.

## Summary

- `bench/tests/test_t4_client_matrix.py`: 33 rows, run with the real `igs104-client` binary in
  the probe container, against the reference server at 172.31.104.10:2404 (common address 45).
  Each row checks the exit status, the message the client prints, and the answers on the wire:
  type ID, cause, and the P/N bit of a confirmation, as tshark decodes them.
- `bench/igs_bench/client.py`: builds the static client into `bench/bin`, as `probe.py` does for
  the probe. `conftest.py` gets a `client_binary` fixture.
- `bench/igs_bench/tshark.py`: a `negative` field on each I frame, read from
  `iec60870_asdu.nega`.
- `bench/peer/server.json`: `time_sync` set to true, and one command point for each command type
  (45-10005 to 45-10010). See the decisions.
- `crates/igs-iec104/src/bin/igs104_client.rs`: fixes a defect found by this matrix (below) and adds
  the `stop` subcommand (STOPDT, see below).

## Defect found: negative confirmations were read as positive

`judge_answer` looked at the cause of transmission only. A negative confirmation (P/N bit set,
101 7.2.3) carries the expected cause, so it was taken for success. The reference server refuses
every command and the clock synchronization with a negative confirmation, so `single 10005
--select` reported exit 0. A direct execution then waited for a termination that never comes.

Fix: a negative answer of the expected kind is a refusal, whatever its cause. Two unit tests
(positive confirmation succeeds, negative confirmation is refused) and one test that another cause
is not judged. `describe` now prints the polarity of each ASDU. The T3 manual check was wrong for
four rows; it is corrected in `docs/ai-log/T3.md`.

## Decisions

- **`stop` subcommand.** T2 has STOPDT (`stop_data_transfer`) but the T3 CLI had no way to reach it.
  `igs104-client stop` starts the data transfer and stops it, each confirmed. It is a small
  addition to the T3 binary, made for this matrix.
- **The client runs in the probe container.** The probe's tcpdump captures its traffic with the
  reference server, as the L4 scenarios do. The static binary is mounted from `bench/bin`.
- **One bench for the matrix.** The reference server starts once (about one minute), and each row
  reads the capture from the frame after its own run.
- **Reconnection is not in the matrix.** A reconnect test restarting the reference server was tried
  and dropped. The probe saw the disconnection ("the peer closed the connection"), then refusals and
  "Host is unreachable" for the whole window. A reproduction showed why: after `podman restart` the
  reference container comes back with its address, but its Fledge service does not run again. Its
  log shows "Starting Fledge" and the container then exits. The bootstrap is written for a first
  boot, so a restart is not a usable fault. The client's reaction (the disconnection, then retries
  with a growing delay) was seen working; the reconnect policy is tested on loopback in T2. A
  reconnect against the reference server needs a fault that does not restart the peer, for example
  a relay that resets the connection, as L5 does for frames.
- **`time_sync` is true in the reference configuration.** With `false` the reference server refuses
  the clock synchronization (negative confirmation). With `true` it confirms it. The server's own
  log then says "Time sync failed" (its clock cannot be set in the container). The matrix checks the
  confirmation on the wire, not that log line.
- **One command point per command type.** Each command goes to its own configured point (45-10005
  for single, 10006 double, 10007 step, 10008 to 10010 for the set-points). The time-tagged variants
  go to the same points. The reference server rejects all of them for the same reason, so the
  choice does not change the outcome, but it keeps each row about its own type.
- **Rows check the refusal where the peer refuses.** A row passes when the client exits as the wire
  shows: exit 0 for a positive confirmation, exit 1 with "refused" for a negative one.

## Observations on the reference server (black box)

- Its plugin does not implement counter interrogation (C_CI_NA_1) or read (C_RD_NA_1). Its log
  says "unsupported command type" and it answers both with cause 44. These two procedures cannot
  be confirmed by this peer in any configuration of the bench.
- Every command is rejected with a negative activation confirmation, select or execute, time-tagged
  or not, for all six command types. Its log says "received while south plugin is not connected".
  The bench has no control path (the image's full start script builds one; the bootstrap does not).
  So no command is confirmed positively here, and no ACTTERM ever comes.
- A group interrogation of a group with no point is confirmed and terminated.
- An interrogation to another common address is refused with cause 7 and P/N = 1, not with cause 46.
  The answer carries the address the client asked for.
- The clock synchronization is confirmed when `time_sync` is true (see above).

## Gate decision

The maintainer chose option 1: the matrix as written is the exit of phase 3. The positive command
path, the counter interrogation and the read against the reference server stay known gaps. A bench task
for a control path is recommended before S5.

## Points for the gate (for the maintainer)

Only 5 of the 33 rows are positive exchanges with the reference server. The other 27 check that
the client reports a refusal, because the peer refuses the request. "100 % of the matrix passes"
holds for the rows as written, but it does not show the positive path of the commands, the counter
interrogation or the read against an independent peer. Options:

1. Accept the matrix as the exit of phase 3, and record the positive command path, the counter
   interrogation and the read as known gaps for this peer. Read and counter cannot be positive with
   this peer's plugin, so they remain gaps in any bench.
2. Open a bench task to add a control path (a dispatcher and a south service connected to the north
   plugin, in the bench compose). It would give positive command confirmations from the reference
   server, and the 24 command rows would then expect them. The effort is larger than the rest of T4.
3. Test the positive command path against the probe as a controlled station. That is our own
   server, not an independent peer, so it is not interop.

Recommendation: option 1 for the exit of phase 3 and a separate bench task for option 2 before S5
(server interop), where a positive command path matters more.

Not decided here: the default common address (1) of `igs104-client`, and whether a command queued
while disconnected should be refused (both open since T3).
