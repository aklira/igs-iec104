# U3 — Client command policy on disconnect, and a transmission event

## Prompt (summarised)

Task U3 of IMPLEMENTATION.md (phase 6). The maintainer validated the recommended API: first make
the order of the client's events certain, then add an `OfflineRequests` policy (`Queue` by default,
`Discard` with an `Event::Discarded`), then a `Delivery::Transmitted` event when the I frame of a
request is written. The maintainer asked to start with a test of the order of the events.

## Status

**In progress.** The order of the events is committed (d09ef39). The policy is done in the working
tree. The transmission event is not written yet.

## First increment: the order of the events

- **Defect.** The supervisor of the client reported `Connected` and `Disconnected` itself, while
  the deliveries of the session went through one forwarding task shared by every connection. When
  the connection ended while deliveries were still on their way, `Disconnected` could overtake
  them, and the deliveries of a connection could even follow the next `Connected`.
- **Test.** `tests/client.rs` `the_deliveries_of_a_connection_come_before_its_disconnection`: a
  station sends ten spontaneous ASDUs and closes the connection; the client has channels of one
  event and a slow reader. Before the fix the test failed five times in five: the tenth ASDU came
  after `Disconnected`.
- **Fix.** Each connection has its own delivery channel and forwarding task. When the session
  ends, the supervisor closes the channel and waits until the forwarding task has handed every
  delivery to the application, then reports `Disconnected`. The documentation of
  `Event::Disconnected` states the guarantee. No public API changed.

## Second increment: the policy for requests made without a connection

- **API.** `OfflineRequests { Queue, Discard }`, a public field `ClientConfig::offline_requests` and
  `ClientConfig::with_offline_requests`; `Queue` is the default and keeps the former behaviour.
  `Event::Discarded(Command)` reports a dropped request. Adding a variant to `Event` breaks an
  exhaustive `match` on it (the client binary had one); this is noted in the CHANGELOG, before 1.0.
- **Behaviour with `Discard`.** The supervisor drops the requests still queued when a connection
  ends (after `Disconnected`), those that arrive while it connects or waits between attempts, and
  those queued when a connection opens (before `Connected`). A request made while the next
  connection opens may still be sent on it; the transmission event of the next increment tells.
- **Redundancy.** `RedundantClient` takes one `ClientConfig` per endpoint, so the policy is set per
  endpoint; the `Discarded` events reach the application as endpoint events.
- **Tests.** `tests/client.rs`: `a_request_made_without_a_connection_waits_for_the_next_one_by_default`
  and `a_request_made_without_a_connection_is_discarded_with_the_discard_policy`, with a station that
  closes the first connection and a STARTDT requested while the client waits to reconnect.
