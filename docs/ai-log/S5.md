# S5 — Server interop, load and switchover (part 1: the interop matrix)

## Prompt (summarised)

Task S5 of IMPLEMENTATION.md: bench scenarios with the reference client, a load test with 50 clients and
10 000 points, and a switchover under load. Depends on S3, S4 and F4. Gate: the phase 4 exit criterion is
reviewed by a maintainer. Done when the interop matrix passes, the load test meets the agreed latency, and
the switchover loses no data.

This log covers the first part only: the interop matrix, with a second reference peer. The maintainer
approved the OpenMUC j60870 library (GNU GPL v3) as that peer, in a locally built image that is not
distributed, and asked for option 1 of the proposal: the matrix with j60870, then the load and the
switchover. The load test and the switchover are not done (see the last section).

Inputs: the server (`crates/igs-iec104/src/bin/igs104_server`), its notes (`docs/igs104-server.md`), the
F4 and T4 bench helpers, and the public API of j60870 as its javadoc describes it (the javadoc jar from
Maven Central, read as documentation). The library's classes were not decompiled and no source was read.

## Summary

- `bench/peer/j60870/Driver.java`: a controlling station that runs one procedure per call (interrogation,
  counter, read, clock, test, reset, the five commands with select and execute, a command to a point that
  takes none) and prints each answer and one `OUTCOME` line. It keeps no protocol logic of its own.
- `bench/peer/j60870/Dockerfile`: builds the driver against the pinned library (version 1.8.0, SHA-256
  checked, the same digests as the independent peer of the MCP project); runs as user 10003. Built locally,
  never pushed.
- `bench/peer/s5/points.toml`: the points of the station under test: 672 (plain, no command), 984
  (normalized), 10005, 10006, 10008, 10009, 10010 (one command each), 20 (counter).
- `bench/docker-compose.yml`: two services in the profile `s5`: `s5-server` (the static `igs104-server`
  binary, at 172.31.104.40) and `s5-peer` (the driver image, at 172.31.104.41). The default services are
  unchanged: the F4 test still passes.
- `bench/igs_bench/s5.py`: builds the static station, builds the driver command, and parses the `OUTCOME`
  line. `bench/igs_bench/compose.py`: `Bench` takes `profiles`.
- `bench/tests/test_s5_interop_matrix.py`: one row per procedure, 13 rows.

## Decisions

- **The peer is a controlling station of the bench, run one procedure per `exec`.** The station under test is
  the controlled side. The outcomes are read from what the library hands to its listener: a row passes when
  the answer has the expected kind (passed, refused, timeout) and, where stated, a detail.
- **Negative answers decide a procedure whatever their cause.** The station refuses a command to a point that
  takes none with a negative answer of cause 47 (unknown information object address), as its notes say. The
  driver accepts any negative answer of the expected type, so the cause is part of the expectation.
- **The test command is checked with its time tag (type 107).** The station answers C_TS_TA_1 only, which is the
  test command of the 104 profile. The matrix checks it that way.
- **Two rows are known gaps, and their expected outcomes say so.**
  - `reset`: the station refuses the reset process command (C_RP_NA_1) with a negative activation
    confirmation. The station does not implement the procedure. Expected: refused. Not a pass.
  - `test-without-time-tag`: a test command without time tag (C_TS_NA_1, type 104, not in the 104 profile)
    gets no answer, and the station closes the connection ("Connection was closed by remote"). Expected:
    timeout. This is a finding for the maintainer: a refusal with a negative confirmation would be
    the usual answer to a type the station does not accept, so the close may be a defect. Not decided here.
- **The reference client (FledgePower) is not a row yet.** A spike showed that it starts the data transfer and
  runs a general interrogation against the station under test (type 100 with cause 6, the station's
  confirmation with cause 7, the points, and the termination with cause 10). Its other procedures could not
  be driven: the south plugin refuses set points and operations (the operation names it accepts are not
  documented, and its source is not read). A row for its general interrogation can be added with its own
  configuration; it is not in this matrix.

## Not done in this part

- **Load test** (50 clients, 10 000 points): needs a load driver and a points file of 10 000 points. Not
  started. The agreed latency is still to be fixed by the maintainer (a proposal: 500 ms p99 for a spontaneous
  change, 200 ms p99 for a command confirmation, 5 s for a general interrogation of 10 000 points).
- **Switchover under load** (two stations in a redundancy group, the active one stopped during the load, no
  data lost): not started.
- **Reference client row**: see the decisions above.
- **Wire capture**: the rows check the peer's view of the answers, not a capture. A capture of the
  station's frames can be added to each row if the maintainer wants the same evidence as T4.

## Status of S5 (after the interop matrix, the load test and the switchover)

- **Interop matrix** (`bench/tests/test_s5_interop_matrix.py`): 13 rows against the j60870 peer. Two rows are known
  gaps, and the rows state them: the reset process command is refused by the station, and a test command without
  time tag (outside the 104 profile) gets no answer and closes the connection. The reference client (FledgePower)
  runs its general interrogation against the station, as the spike showed; its other procedures are not reachable
  through the plugin, so it is not a row.
- **Load test** (`bench/tests/test_s5_load.py`): one session per rate, from 50 to 1 000 changing points. The
  station's failures under load came from the TCP delay and from the retry timer of its send loop, both
  corrected (`docs/ai-log/S5-nodelay.md`, `docs/ai-log/S5-window.md`). Every rate passes: an interrogation under
  load takes about 0.63 s (p99, threshold 5 s), a change waits at most for the interrogation in progress (the
  maintainer's decision), and every command is confirmed within 1 ms (threshold 200 ms).
- **Switchover under load** (`bench/tests/test_s5_failover.py`): one connection for 30 s, then a second connection
  that starts the data transfer and supersedes the first, with 200 changing points. 10 986 changes received, 5 512
  on the first connection and 5 474 on the second; no gap and no reordering for any point; one change repeated;
  nothing arrives on the first connection after the second starts.

S5 is not ticked in `IMPLEMENTATION.md`: its exit criterion is a human gate. For the maintainer to review:
the two known gaps (reset, and the test command without time tag), the interpretation of "50 clients" as
50 sessions one after the other (a station starts one connection at a time), the rule that a change waits at
most for the interrogation in progress, and the reference client row that is not in the matrix.
