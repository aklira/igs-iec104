# T3 — `igs104-client` binary

## Prompt (summarised)

Task T3 of IMPLEMENTATION.md: a command-line client (clap) to connect, interrogate, send
commands and print the decoded ASDUs. Done when `--help` is documented, and a manual check
against the bench server is recorded here.

Inputs: the client API of T2 and the procedures of §7 (already read for T2). `clap` is named
in the plan for this task.

## Summary

`crates/igs-iec104/src/bin/igs104_client.rs`:

- Global options: `-a/--address` (the station, default 127.0.0.1:2404), `-c/--common-address`
  (default 1), `-t/--timeout` (seconds for the connection and for each confirmation, default 10).
- Subcommands: `monitor [--for SECONDS]`, `interrogate [--group 1..16]`,
  `counter [--request 1..63] [--freeze read|freeze|freeze-reset|reset]`, `read ADDRESS`,
  `clock-sync`, `test [--pattern N]`, `single ADDRESS [--off] [--select] [--time]`,
  `double ADDRESS [--off] [--select] [--time]`, `step ADDRESS [--lower] [--select] [--time]`,
  `set-point ADDRESS --kind normalized|scaled|float --value V [--select] [--time]`.
- Each procedure starts the data transfer, sends its request, and waits for the confirmation:
  the ACTCON of a select, the ACTTERM of an execution, the ACTTERM of an interrogation or a
  counter interrogation, the answer to a read, the ACTCON of a clock synchronization or a test.
- Every event is printed while waiting: the connection, the transfer state, and each ASDU in a
  decoded form (its type, its cause with a name, its common address, its objects).
- Exit status: 0 when the confirmation arrives in time; 1 on a refusal, a timeout or a
  connection error (the message on standard error); 2 on a usage error (clap).

## Decisions

- **A refusal is a failure.** A negative cause (44 to 47, §8.9) answering the request ends the
  command with its name, rather than a timeout.
- **Times are UTC.** The clock of the machine is converted to CP56Time2a without a date
  library: a date conversion in the binary, checked and unit-tested with known Unix times.
  Years 2000 to 2099 only.
- **Monitor runs until stopped** unless `--for` is given. It prints every event.
- **The common address defaults to 1.** Most stations answer only to their own address; the
  reference server uses 45 (see below). The default is a placeholder for the operator to set.
- **Commands are split.** A select and its execution are two runs, as §7.7 describes, so that
  a command can be checked between the two.
- **Lints as in the crate.** The binary has no `unwrap`, `expect`, indexing or unchecked
  arithmetic; arithmetic on dates is `checked_*`.

## Manual check against the bench server

Set-up: the reference server (`ref-server`, 172.31.104.10) and the probe container, which runs
the static client (`bench/bin/igs104-client`, built with
`cargo build --release --target x86_64-unknown-linux-musl -p igs-iec104 --bin igs104-client`).
The host cannot reach the bench subnet with rootless Podman, so the check runs in the probe
container. Each run was made with `-t 8` (or 6) and read with its exit status.

| Command | Exit | Outcome |
| --- | --- | --- |
| `monitor --for 3` | 0 | connected; transfer PendingStarted, then Started; nothing spontaneous in 3 s |
| `-c 45 interrogate` | 0 | ACTCON, the points 672 (M_SP) and 984 (M_ME), then ACTTERM |
| `-c 65535 interrogate` | 0 | the same answer, from the global address |
| `-c 1 interrogate` | 1 | ACTCON with common address 1, then no ACTTERM within 8 s; the station's own address is 45 |
| `-c 45 clock-sync` | 0 | ACTCON (C_CS_NA_1, cause 7) |
| `-c 45 test` | 0 | ACTCON (C_TS_TA_1, cause 7) |
| `-c 45 single 672 --select` | 0 | ACTCON (C_SC_NA_1, cause 7) |
| `-c 45 single 672 --time` (execute) | 1 | ACTCON (C_SC_TA_1, cause 7), no ACTTERM within 6 s |
| `-c 45 read 672` | 1 | refused: unknown type identification (cause 44) |
| `-c 45 counter --request 1` | 1 | refused: unknown type identification (cause 44) |

Observations on the reference server, black box:

- It answers the general interrogation, the clock synchronization, the test command and the
  select of a single command, all with cause 7.
- It refuses the read (C_RD_NA_1) and the counter interrogation (C_CI_NA_1) with cause 44,
  unknown type identification. The reason is not visible from outside.
- After the execution of a time-tagged single command it gives ACTCON and no ACTTERM within 6 s.
  This is the behaviour the client must report, and it does. The bench server's
  `cmd_exec_timeout` is 20 s; a longer wait would show whether the termination comes later.

## Points for the reviewer

- The default common address (1) matches no reference station. A maintainer may prefer a
  required option.
- The output is the `Debug` form of the decoded body: complete, but verbose. A field-by-field
  rendering for each type would be a later refinement.
- The single-command execution ends with ACTCON and no ACTTERM on the reference server. Whether
  it should terminate is for the L4 scenarios to decide, or a maintainer; the client waits for
  the termination the standard names.

## Correction (found in T4)

The manual check above is wrong for four rows. `judge_answer` read the cause of transmission
only and ignored the P/N bit, so a negative confirmation counted as a positive one. The
reference server confirms every command and the clock synchronization negatively when it refuses
them (its control path has no south plugin connected, and its clock synchronization was
disabled at the time). The rows that change are:

- `-c 45 clock-sync`: reported exit 0; the confirmation was negative (cause 7, P/N = 1).
- `-c 45 single 672 --select`: reported exit 0; negative confirmation.
- `-c 45 single 672 --time`: reported "no ACTTERM within 6 s"; the answer was a negative
  confirmation, which the client ignored. There is no termination to wait for.
- `-c 1 interrogate`: exit 1 for the right reason only by chance: the negative confirmation was
  taken for a missing termination.

The rows for the general interrogation, the test command, the read and the counter interrogation
(cause 44) were judged correctly. The correction is in T4: negative confirmations are refusals,
with unit tests (`docs/ai-log/T4.md`). The "no ACTTERM on the reference server" observation
recorded above is not a peer behaviour and is withdrawn.
