# C5 — APCI framing

## Prompt (summarised)

Task C5 of IMPLEMENTATION.md: `Apdu` with an I-format variant (N(S), N(R) and
ASDU), an S-format variant (N(R)) and a U-format variant with the
STARTDT/STOPDT/TESTFR act and con functions. An incremental `FrameDecoder`
accepts arbitrary byte chunks, returns complete APDUs, reports framing
errors, and never buffers more than one maximum APDU. Done when tests feed
frames split at every byte boundary and concatenated frames.

Inputs read: `104/sections/005_5_*` (APCI: start, length, control field) and
`104/sections/004_4_*` (protocol structure, no APCI content).

## Source of the bit positions

The cleaned text of §5 marks figures 4 to 8 as missing. The figure text is in
the raw pages of the standard (`104/raw/page_0035.md`, figures 6 to 8, OCR of
the diagrams). The positions used in the code are taken from that figure text:

- I format: bit 1 of the first control octet is 0; N(S) is bits 2 to 8 of
  octet 1 (bit 2 is the least significant) and octet 2; octet 3 has bit 1 = 0;
  N(R) is bits 2 to 8 of octet 3 and octet 4.
- S format: octet 1 is 01H (bits 1 and 2 = 1 and 0); octet 2 is 0; octet 3 has
  bit 1 = 0; N(R) as above.
- U format: octet 1 has bits 1 and 2 set and one function bit: STARTDT act
  bit 3, STARTDT con bit 4, STOPDT act bit 5, STOPDT con bit 6, TESTFR act
  bit 7, TESTFR con bit 8. Octets 2 to 4 are 0.

These give the six U codes 07H, 0BH, 13H, 23H, 43H and 83H. The start octet
(68H), the length range (4 to 253, counting the control field and the ASDU)
and the 249-octet ASDU limit are in the clause 5 text.

## Summary

- `crates/igs-iec104-codec/src/apci.rs`:
  - `SequenceNumber`: 0..=32767, `next` wraps from 32767 to 0.
  - `UnnumberedFunction`: the six U functions, one per frame.
  - `Apdu`: `Information { send, receive, asdu }`, `Supervisory { receive }`,
    `Unnumbered(function)`. `Apdu::decode` reads one complete frame and checks
    the start, the length, the control field and the body. `Apdu::to_vec`
    writes the frame.
  - `FrameDecoder`: `next_frame(&mut input)` takes octets from the front of
    `input` and returns one frame when it is complete. When the input runs out
    first it returns `None` with the input empty. The start and length octets are
    checked as they arrive.
- `error.rs`: `DecodeError` gains `FrameStart { found }`, `FrameLength { length }`
  and `InvalidControlField { control }`.
- `asdu/mod.rs`: uses the control field constant from `apci`, one copy only.
- `lib.rs`: wires `pub mod apci;`.

Verification: `cargo fmt --all --check`, `cargo clippy --workspace
--all-targets --all-features -- -D warnings`, `cargo test --workspace
--all-features` (97 tests, of which 15 are APCI tests) and `cargo deny check`
are all green.

What the tests show:

- Hand-written frames for each format: I(1, 0) with the C_IC_NA_1 interrogation
  ASDU, S(5), the six U functions, I(32767, 32767). Each decodes to its
  variant and encodes back to the same octets.
- The stream of all these frames, cut at every byte boundary into two chunks,
  gives the same frames in the same order. The same stream fed one octet at a
  time gives the same frames, and so does the concatenated stream in one chunk.
- `next_frame` takes only the octets of one frame: the rest of the input is
  left for the next call.
- A maximal frame (length 253, 255 octets) is held until its last octet, and no
  octet after it is taken.
- A bad start octet, and the lengths 0, 3, 254 and 255, are framing errors. The
  error is sticky. The smallest length (4) is accepted.
- `Apdu::decode` rejects: a bad start, a truncated frame, a length that does not
  match the frame, octets after the frame, and invalid control fields (I with
  bit 1 of octet 3 set, S with a bit above bit 2 or a non-zero octet 2, U with
  zero or two functions, U with non-zero octets 2 to 4, S or U with an ASDU).
- An I frame with a type outside the profile is reported as
  `UnsupportedTypeId`, and the decoder goes on with the next frame.

## Decisions

- D-011 (PROVENANCE.md): a framing error is sticky. The decoder never tries to
  resynchronise on a later start octet, because the boundaries are lost.
  The standard text read for this task is silent on the receiver's behaviour.
- The frame decoder returns a copy of each frame (`Vec<u8>`), so the caller can
  keep frames while it reads the next one.
- `Apdu::decode` takes one frame, not a stream. The stream is split by
  `FrameDecoder`, so an ASDU that fails to decode does not desynchronise the
  stream: the frame is still cut at its length.
- `SequenceNumber` is a private value with a range check in `new`. The control
  octets are read and written by the bit positions above only.

## Points for the reviewer

- The bit positions come from the figure text in the raw pages, which the
  cleaned text does not contain. A maintainer should check figures 6 to 8 against
  the PDF once, since the OCR of the diagrams is the only source for them here.
- `FrameDecoder` holds at most one frame: a `Vec` of up to 255 octets. The
  allocation is per frame; there is no pool.
- Size: `apci.rs` has about 310 lines of code and about 330 lines of tests. The
  code is under the 400-line guideline.
